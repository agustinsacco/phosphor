# Host Brain wire and CLI

Brain is owned by one Host. Its surface protocol doesn't send database paths, transcript paths, a claimed actor, a provider credential, an agent token, or a target Host in operation arguments. The connection is the target. It doesn't accept a batch, and it isn't an entry point for curator tools. The reserved Brain lane is not a generic lane subscription target.

## Negotiation and rights

`ready.brain: true` means this listener has a native Brain surface binding. Absence means unsupported, not disabled. The status query distinguishes disabled and available store/model states. A new client sends nothing to an unsupported Host and never falls back to a Desktop store. Older v1 parsers ignore the additive keys. No Brain right is in either v1 capability array.

Control only signs `brainAccess` when explicitly requested on the owner-authorized, single-Host grant issue route. Each grant is independent. A machine-origin grant cannot carry these rights. A supporting Host echoes effective `brainAccess` on `ready` and `auth-renewed`. Missing rights on renewal mean none; losing a right invalidates previously admitted work even if the right is later restored. Work must check live admission at the mutation boundary as well as result delivery. An attested local owner receives all rights; ordinary sockets do not.

| Right                | Surface                                                                                                             |
| -------------------- | ------------------------------------------------------------------------------------------------------------------- |
| `read`               | Redacted summary, bounded jobs/changes and graph, Ask, entities and paths                                           |
| `evidence` + `read`  | Source excerpts and detailed memory evidence                                                                        |
| `configure` + `read` | Settings (including configured reader model), queue/jobs, model admin, Defrag, undo, and owner or knowledge changes |
| `control`            | Stop Brain Agent's running turn (`brain:laneStop`) only. It returns no conversation data                            |
| All four rights      | Brain Agent's conversation: Show, Watch, Send, Take, dialog answers and Tell                                        |

The conversation shows what Brain Agent read, evidence included, and drives its changes to knowledge, so every conversation method needs `read`, `control`, `evidence` and `configure` (`brainRequiredAccess`). Stop needs `control` alone and still checks the turn it names, the current fence and the controller. A grant user also needs the `sessions.control` capability for every method that acts on Brain Agent's lane, Stop included (`brainActsOnAgentLane`); losing it on renewal revokes admitted work like losing a Brain right. Clients offer a method only when `brainClientMayInvoke` allows it, and the Host decides again on every call.

## Off, enabling and ownership

A Host binds the surface only when its bundle is qualified (`resolvePackagedBrainRuntime`); an unqualified Host advertises no `ready.brain`, starts no worker and leaves ordinary lanes on the Desktop bridge. Both listeners serve the one binding run builds, so they share approvals and limits.

A Host with no Brain store is off and creates nothing to say so. `brain:status` and `brain:prefs` answer with Brain off and the fixed generation `00000000-0000-4000-8000-000000000000` at revision 0; every other method refuses `disabled`. The one write it takes is `brain:setPrefs` with `enabled: true` and that stamp, which creates the store and applies the settings. The local CLI does this through one approval like any other write.

The Host creates a store only when no move claims it and Desktop's own Brain is unknown to the owner socket. Otherwise the request refuses `unavailable`: a Mac whose Desktop has a Brain moves it with the handover instead of starting a second one. Once a store exists, every entry point and every write rechecks that no move claims it and that the Host is not shutting down. A Brain the Host does not own at that moment answers `unavailable`, never data from a copy.

Lane IDs resolve through the Host's lane store and the session ID in the transcript's own header. A reserved lane, a transcript that is a symbolic link and a transcript without a pi header resolve to nothing.

## Commands and transport

`HostBrainRequest` and `BRAIN_METHODS` are the allowlist (`libs/shared/src/host-brain{,-request}.ts`). A read is an `ops.run` call with `{op: 'brain.surface', args: request}`. A mutation is a laneless `ops.run` command, answered by a receipt. They are handled before the general ops dispatcher and don't enter its audit log. A reply contains a reviewed projection or a fixed refusal; structured operational errors never return runtime stderr or provider error strings. The adapter suppresses Brain traffic payloads, including approval traffic. Brain commands are not replayed or retained as private receipts across disconnect. An uncertain write is never a cue to resend it.

`hostBrain(connectionForHost).invoke({hostId, connectionToken}, request)` gates support and rights before sending and drops an answer on connection replacement or authorization loss. Write requests marked as guarded carry `{expected: {generation, revision}}`. Revision-guarded mutations require both values; if the original positional revision is also present it must agree. Queue/cancel/retry/reread check the generation and current lane/job state. The runtime compares the stamp under the actual writer boundary, never an unrelated asynchronous status read. `stale` means the caller should refresh, not replay.

`brain:laneState(laneId)` reports explicit exclusion, the active job, and the latest read for one caller-visible Host lane. Settings never return or accept the stored pi exclusion IDs; saving settings preserves them. Use `brain:neverRead` with the Host lane UUID to edit one exclusion. `brain:entityMemories` accepts `filter.laneId` and refuses an unknown or invisible lane without broadening the query. Job and memory provenance is not a routing ID. Extraction and memory detail return `sourceLaneId` only when the current caller can open the exact saved session and owned transcript; unavailable extraction transcripts have no source segments. Conversation calls use the single reserved lane. Show returns its bounded latest page; continuation uses a Host-issued cursor. Watch is a bounded read, not a subscription, and refreshes the current page. Mutations use the current controller fence; `self` is derived from the connection client, not a claimed actor. The page's `turn` is an opaque reference to the running turn the caller started, or null. Stop takes `[fence, turn]` and ends only that turn, while it runs, for the person who started it; a stale or unknown reference refuses `stale` and aborts nothing, so a delayed Stop or a late CLI redemption never ends a later turn. Defrag's turn has no reference and is stopped only through Defrag. The page lists only the questions the caller can answer: those asked in the current process by the turn the caller started. An answer uses the controller checks and the question's ID, once; a question from Defrag, an earlier turn or a replaced process is refused `not-found` and ends on pi's own timeout. Tell is a write to the reserved lane, not a search or a path-returning operation.

## Brain Agent's turns

A person's message (Send or Tell) runs only from a qualified interactive launch (`apps/host/src/brain/agent/profile.ts`). Qualifying a launch takes proof that pi loads only the extensions the Host names and that every tool, provider-native ones included, reaches the guard's `tool_call`; a provider name or a document is not that proof. **No production launch qualifies yet**, so every Send and Tell refuses `unavailable` before pi starts, control changes or a transcript binds, and the page says `messaging: false`. Show, Watch, Take and the saved conversation still work, and Defrag is unchanged. Working conversation on a Host is not delivered by this.

A qualified launch would load `brain-ext/brain-agent-guard.mjs`, whose `tool_call` hook blocks every tool except Brain Agent's own `brain_*` tools. The conversation checks `get_commands` and `get_state` on the exact live process before accepting it as interactive and before handing off a prompt. Those reports are consistency checks, not qualification: they cannot attest which code ran or that every effect goes through the guard. A missing guard or model mismatch refuses `unavailable`. The prompt also rechecks the controller's authority and fence at dispatch, after session-service preflight. Messages in command form (starting with `/` or `!`) are refused before they reach pi, because pi runs those outside the guard.

Defrag keeps the broad tool profile. One process runs at a time: switching profiles resolves the saved binding after the previous turn has settled and the process has stopped. The new process must report a path in the reserved lane's pi session directory, and when resuming a saved transcript it must report that exact path before the Host publishes the process or binds it to the lane. A report of a different file cannot redirect the saved page. A message never restarts the lane under Defrag (it answers `busy`). A new process starts with no turn or question from the one it replaced. See [packaging](host-brain-packaging.md#brain-agent-execution-is-not-qualified) for the separate launch blocker.

Each turn is named before its prompt is sent: a controller's message or Defrag's. Brain Agent's curator tools answer only under the running turn's gate (`BrainAgentHost.turnGate`, `libs/brain-runtime/src/agent/curator-turn.ts`). A call is bound to the turn running when it arrives, and the gate is checked again immediately before the write, after any awaits. A late call never borrows a later turn's authority or Defrag's. A controller turn writes only while the person who started it keeps their authority, and is journaled under no Defrag run. A Defrag turn writes only while that same run answers. A turn of unknown identity gets no tools. An admitted Stop closes that turn's curator gate immediately, before pi receives or acknowledges `abort`. In-flight calls cannot commit after the gate closes; changes already committed stay. An abort is sent only if the same turn and process still match at dispatch. When a controller's authority lapses, the Host also closes the gate and aborts that exact turn, checked on every event and on a short timer. The runtime's unattributed `tell` is refused on a Host. Desktop's Brain lane has no gate and is unchanged.

## CLI approval

On a Host serving the private Unix listener, `phosphor brain status --host local --json` reads the selected Host. `brain queue --host local --expected GENERATION:REVISION --args '["LANE_UUID"]'` queues an opaque admitted lane. See `phosphor brain --help` for the reviewed subcommands (including `lane show`, `lane watch`, `lane send`, `lane stop`, `lane answer`). Default textual output is fixed; use `--json` to explicitly request approved structured content. Named remote and fleet targets are refused, not routed through a machine grant or to another store. The secure alternative is to use the authenticated Brain surface for that selected Host, or run the CLI in a terminal on the target Host and approve its one local request from the authenticated surface. If the target has no serving private socket, only the authenticated surface is available.

The CLI is an unsigned local principal. Every Brain operation, even a sensitive read, needs one authenticated owner surface to approve it on that same Host. `brain.approval` supports status for the issuing socket, and list/answer for authenticated viewers with the required rights. It reuses the confirmation digest and expiry rules in an isolated namespace. The approved request includes exact args and the expected stamp; only the original connection can redeem it once, while the approving rights remain live. The redeemed operation acts as the authenticated approver's client for that one request: a CLI that sends a message, takes control, stops or answers is the approver as controller, never a label or client ID the CLI supplied. Each redemption has its own approver, so two approvers are two controllers, and a stop-only approver cannot stop or answer as another person. An approver can approve only what they could do themselves, and losing their authority revokes the running operation. A restart or loss of the requesting connection voids it. The confirmation title does not print prompts, paths or other raw content. `lane watch` returns one approved page. If the Host lacks the socket, an approval surface or an issued grant, no CLI operation is performed; it never silently falls back to TCP or the legacy Brain.
